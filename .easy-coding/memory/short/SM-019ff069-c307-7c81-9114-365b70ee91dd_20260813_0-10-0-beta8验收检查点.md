## Technical Memory Candidates

- Architecture / Interface Decisions: VERIFICATION 成功只形成 Harness 验证证据；Canonical 在确认应用 VERIFICATION → MEMORY 时才写 `verified`，MEMORY → COMPLETE 才写 `completed`。
- Engineering Rules / Workflows: 无漂移时 Auto 可继续自动流转；检查点后新增代码漂移只暂停一次并展示精确差异，用户确认后复用 REVIEW，按 carry-forward/targeted/waived 明确处理验证证据。
- Implementation Patterns / Reusable Approaches: 验收快照覆盖 Git 与计划内非 Git 文件，文本、二进制、mode 变化均记录逐文件 old/new SHA-256，并以稳定 digest 绑定授权、Canonical 投影和短期记忆。
- Pitfalls / Fix Strategies: 多任务 Canonical 的 targeted 验证必须覆盖实际受影响 source task；短期记忆不能只记录 digest，必须同时保留授权来源、审批/Review/验证策略、摘要、变更文件与受影响 source task。
- Compatibility Boundary: 用户新提出的修复仍进入 IMPLEMENT/REVIEW；只有既有验证检查点之后、已展示并获用户确认的保存差异可免重复 REVIEW。
