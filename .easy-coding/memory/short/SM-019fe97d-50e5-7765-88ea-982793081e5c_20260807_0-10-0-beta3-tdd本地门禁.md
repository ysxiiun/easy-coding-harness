# 0.10.0-beta.3 TDD 本地验收门禁

## Task Summary

- Goal: 移除 TDD 业务任务对远程 GitLab pipeline 成功证据的依赖，避免本地验证通过后仍因 CI 取证被迫中间提交推送。
- Scope: 共享状态 API、ExecutionRecord 类型、TDD 阶段 skills、主约束模板、初始化说明、文档、版本和回归测试。
- Result: completed；TDD 验收现在要求通过的本地单测和达到冻结阈值的本地 JaCoCo changed-line coverage，不再要求 pipeline URL、job identity 或远程 success 状态。
- Key Constraints: `ec-tdd-init` 仍在 TDD 关闭态生成并校验 GitLab CI/readiness；初始化完成后再显式开启 TDD 的顺序不变；TDD 默认关闭、Java-only、默认阈值 90%、RED/GREEN/REFACTOR 与独立 TDD review 均保持不变。
- Workflow Mode: standard；改动横跨状态机、证据契约、安装模板和文档，需要完整回归但不涉及新架构或高风险数据迁移。

## Technical Memory Candidates

- Architecture / Interface Decisions: GitLab CI 是由 `ec-tdd-init` 生成的项目自动化基础设施，不是 Harness 业务任务的验收依赖；`VERIFICATION -> MEMORY` 只消费本地单测与本地 changed-line coverage 证据。
- Engineering Rules / Workflows: 每个 TDD 仓库（Canonical 场景下每个 source task）必须有通过的本地 `check_type=test` 记录和 `coverage_scope=local` 记录；覆盖率继续绑定任务冻结 baseline、阈值、报告路径与 SHA。
- Implementation Patterns / Reusable Approaches: 在构建最新验证证据集合时先忽略历史 `coverage_scope=gitlab` 记录，使 beta.1/beta.2 的 pending/failed 远程证据无需迁移即可退出验收。
- Pitfalls / Fix Strategies: 只删除 GitLab scope 检查会让 Fast TDD 可能仅凭 coverage 通过；修复时必须同时补齐本地单测机械门禁。不要删除 readiness 对生成 CI 文件的静态检查，否则会破坏“先初始化、再开启”的无循环顺序。
- Verification Experience: 状态机测试必须覆盖缺少本地单测、错误 baseline、可变 `HEAD`、CI 文件 readiness 漂移、历史远程失败不阻塞以及安装后 skill 不再包含远程证据字段。
