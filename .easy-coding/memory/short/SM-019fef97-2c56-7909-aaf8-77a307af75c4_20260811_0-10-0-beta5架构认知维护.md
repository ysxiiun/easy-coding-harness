## 技术记忆候选

- 架构 / 接口决策：日常任务生产事实；长期记忆治理事实；架构维护只消费冻结的稳定事实。`distill` 才触发架构评估，默认 `no-op`。
- 工程规则 / 工作流：评估结果写入 `memory_progress.architecture_assessment`，包含 action、trigger、reason、evidence、affected_sections 与架构资产指纹。
- 实现模式 / 复用写法：架构评估必须在消费短期候选前完成；`backfill/update` 只定向修改 ABSTRACT 受影响章节并创建或追加 `.easy-coding/CHANGELOG.md`。
- 易错点 / 修复策略：不能把“进入 MEMORY”当作更新架构的理由；不能让迭代项目利用缺失 ABSTRACT 走 startup 回补；不能在评估失败后先删除候选。
- 验证经验：状态 API 需要同时覆盖新指令机械门禁、资产误变、候选顺序、缺失 ABSTRACT 的项目模式判断，以及旧 MEMORY 指令兼容。
